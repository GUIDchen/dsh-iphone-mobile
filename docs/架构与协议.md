## dsh web 的真实接口面（已核实，非推测）

- HTTP：/api 前缀承载全部 RPC。GET /api 返回 404；GET /api/events.mux 返回 426（该路径只接受 WebSocket 升级，没有 SSE 回退）。
- WebSocket：/api/events.mux 与 /api/events.host 两条下行流，只推送 ServerRequest 文本消息，客户端不得在其上发送应用数据。
- 信任围栏：/api 请求的 Host 必须是 loopback 或 --trusted-host 声明的权威；带 Origin 时必须与 Host 一致，显式 cross-site 直接拒绝。实测：Host: dsh.example.com 直连返回 403。
- 围栏是可达性策略，不是鉴权层。
- 监听只支持 127.0.0.1 与 0.0.0.0，且官方明确在远程访问有鉴权层之前不支持 0.0.0.0。

## mux 下行流的帧契约（来自 dsh 权威类型定义）

每帧是一层信封：{ type: 'server-request', rpcId, method, payload }，payload 为下列之一：

| payload.type | 含义 | 对推送的意义 |
| --- | --- | --- |
| session/subscribed | 该会话已订阅，带 lastSeq | 基线帧，不通知 |
| session/event | 会话事件透传（含 seq、time、data） | turn/end 等可用于完成通知 |
| approval/requested | 需要用户批准（带 approvalId、toolName、reason） | 最高优先通知 |
| approval/resolved | 批准已决议 | 不通知 |
| question/requested | 需要用户回答（questions 数组） | 高优先通知 |
| question/resolved | 提问已决议 | 不通知 |
| session/jobs | 该会话可见的全部后台任务快照 | 终态变化通知完成/失败 |
| session/projection | 投影单体更新 | 不通知 |
| stream/error | 流级错误 | 不通知 |

- session/event 的 event.type 词表：turn/start、turn/end、step/start、step/end、tool/call、tool/result、assistant/chunk、assistant/message、user/message、session/title、session/created、session/disposed 等。
- 每个会话事件带单调 seq；session/subscribed 的 lastSeq 是该会话当前水位。

### 关于断点续传的重要更正

早期文档按「SSE + since 游标回放」设计，这是错的：契约明确写着 mux 的 since 参数在 v1 **未实现**（传入会被忽略），
并且「重连 = 重新打开流 + 重新拉取历史」。同时，打开流时宿主会**自动重放仍未处理的 approval/question 帧**。

因此正确的续传语义是：

1. 重连即重开流，不要指望服务端按游标补发。
2. 用每条事件的 seq 做去重与排序；用 session/subscribed 的 lastSeq 判断自己落后多少。
3. 落后较多时主动重新拉取历史，而不是等待补发。
4. 未处理的审批会随流重放，因此「锁屏期间错过的审批」不会丢失。

~~~mermaid
sequenceDiagram
  participant P as iPhone
  participant G as gateway
  participant W as dsh web
  P->>G: 打开 WebSocket /api/events.mux
  W-->>P: session/subscribed (lastSeq)
  W-->>P: 宿主动重放未处理的 approval/requested
  Note over P: 锁屏，socket 断开
  P->>G: 重开流（不传游标）
  W-->>P: 重新订阅 + 重放在处理中的审批
  P->>P: 按 seq 去重，落后则重拉历史
~~~

## 推送设计（已实现）

- 网关启动时作为 mux 客户端连上事件流，按上表把帧映射成通知（纯函数 notificationsForFrame，可单测）。
- 任务终态去重：session/jobs 是全量快照，只在状态跃迁到 completed/failed/killed 时通知一次。
- turn/end 按 seq 去重，避免重放导致重复提醒。
- 加密：自实现 RFC 8291 aes128gcm + RFC 8292 VAPID（node:crypto 的 P-256 / HKDF / AES-GCM），
  不引第三方依赖，且可离线运行；正确性由 scripts/selftest-webpush.mjs 做真实往返验证。
- 失效订阅：发送返回 404/410 即删除该订阅（自愈）。
- 订阅入口：注入的按钮只在「未订阅且权限未被拒绝」时出现，且必须由用户点击触发（iOS 要求）。

## 网关为什么这样设计

1. 代理：转发到 127.0.0.1:3080，Host 重写为 loopback、删除 Origin 与 sec-fetch-site，围栏无需 dsh 侧改动即可通过；
   WebSocket 走 upgrade 后与上游建 TCP、重放重写后的握手再双向 pipe（因此不需要 ws 依赖）。
2. 鉴权：对外用访问令牌换 HttpOnly Cookie，因为围栏本身不提供认证层。
3. 移动端层：对 text/html 注入 manifest、图标、移动端样式、Service Worker 与订阅入口。
   改写 HTML 后必须去掉上游 chunked 编码并改成定长（曾漏掉，导致浏览器解析失败，已修）。

## 关于 dsh GUI 的两条事实核实（影响移动端设计）

1. **GUI 没有 URL 路由**。客户端产物中搜不到 pushState / replaceState / hashchange，页面里也没有 a[href]，
   会话切换只发生在内部状态里。结论：**通知无法用 URL 深链到某个具体会话**，当前通知的 url 一律为 '/'，
   会话信息放在通知正文里。要做真正的深链，前提是 GUI 先具备可寻址的会话路由。
2. **GUI 自身已有窄屏适配**：存在 width<=560px（4 处）、<=680px、<=720px（2 处）、<=760px 的媒体查询，
   以及 pointer:coarse 分支。因此 public/mobile.css 不重复造断点，只补它没有的部分：
   安全区（env(safe-area-inset-*)）、输入控件 16px 字号防 iOS 自动放大、44px 触摸目标、长代码与表格的横向滚动。

## 安全模型

- dsh web 只监听 127.0.0.1；对外只有网关一个入口。
- 网关令牌换 HttpOnly Cookie；公网入口建议叠加 Cloudflare Access。
- 密钥与订阅文件放 ~/.dsh-mobile，权限 0600，不进仓库。
