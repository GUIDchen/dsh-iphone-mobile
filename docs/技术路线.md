# 技术路线

## 目标

在 iPhone 上远程控制本机运行的 DeepSeek Harness：查看会话、审批工具调用、中断任务、浏览文件与使用终端。
约束：会话数据留在本机；需要外网可达；体验要接近原生。

## 同类项目调研

| 项目 | 形态 | 关键做法 | 借鉴点 |
| --- | --- | --- | --- |
| dsh web（本机已有） | 浏览器 GUI | 会话、工具调用、审批已在浏览器内可用 | 直接作为基座，移动端做适配而非重写 |
| Happy | 原生 App + 自建中继 | 包装 CLI，手机接管会话，端到端加密，推送完善 | 说明了「可靠推送 + 原生手感」的代价：中继与上架 |
| VibeTunnel | 浏览器终端 | 把 PTY 代理进浏览器，主打离开工位盯 agent | 终端页可复用其思路，不必自研协议 |
| Claude Code Remote Control | 本机会话 + 云端中继 | 会话继续权在本机，手机只是控制面 | 与本项目定位一致，方向正确 |
| code-server / VS Code Web | 浏览器 IDE | 终端与编辑体验完整 | 过重，无会话语义 |
| ttyd / gotty | Web 终端 | 极简 PTY 转发 | 仅作终端兜底 |

## 外网访问方案对比

| 方案 | 底层机制 | 手机端要求 | 稳定性 | 结论 |
| --- | --- | --- | --- | --- |
| Tailscale 私有网络 | WireGuard 组网，优先 UDP 直连，打洞失败回退 DERP 中继 | 必须安装 App 并登录 | 较稳但依赖网络条件，中继时延迟升高 | 首选（私密、零暴露） |
| Cloudflare Tunnel + Access | 本机 cloudflared 只做出站连接到 CF 边缘，公网只访问标准 HTTPS | 无需安装任何客户端 | 最稳，任何网络都视为普通 HTTPS | 次选（需域名） |
| Tailscale Funnel | 经 Funnel 中继服务器做 TCP 代理 | 无需安装 | 官方标注 beta；仅支持 443/8443/10000 端口；流量有不可配置的带宽限制 | 不推荐 |
| 自建 VPS 反代 | 公网 IP + 证书 + 自建鉴权 | 无需安装 | 取决于线路，且本机服务真实暴露在公网 | 进阶备选 |

要点：Funnel 的端口与带宽限制对「长对话 + 终端」这类持续流量是硬伤；Tailscale 的稳定性取决于打洞是否成功，
这正是 Cloudflare Tunnel 的 outbound-only 模型更稳的原因。

## 选型结论

1. 基座：复用 dsh web，做移动优先的 PWA（零分发、零审核、随桌面端升级）。
2. 通道：Tailscale 先行（无需域名即可开工），域名到位后叠加 Cloudflare Tunnel + Access，双通道可切换。
3. 推送：先 Web Push（VAPID），再把高价值通知交给 Capacitor 壳 + APNs。
4. 终端：xterm.js，不自研协议栈。

## 被否决的路线

- 全量 React Native / Expo：界面与 schema 渲染层要重写，且需要自建中继，成本远超收益。
- 纯 SwiftUI 原生：仅 iOS，成本最高，迭代最慢。
- 纯 PWA 不上壳：无法解决「关闭隧道即收不到推送」，作为兜底保留而非终态。
